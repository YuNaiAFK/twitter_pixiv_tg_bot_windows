## 這是什麼

機器人設計成**公開**的：任何在群組裡看得到它的人都能貼連結、拿到結果。
管理機器人是另一回事 —— 只有管理員能碰，而且管理權限刻意與「能不能貼連結」分開。

X／Twitter 結果以「原始連結」超連結文字嵌入來源網址，可用 `ATTACH_SOURCE_LINK=0` 關閉；Pixiv 文件不附來源連結。
解析成功時只送出結果，不附加任何說明；失敗時只回一行話，技術細節寫進日誌而不是聊天室。

### 訊息如何被路由

| 訊息內容 | 機器人做的事 |
| --- | --- |
| `x.com` / `twitter.com` 作品連結 | 下載媒體；圖片以相簿送出 |
| `pixiv.net` 作品連結 | 下載作品，以**原始檔案**相簿送出 |
| `e-hentai.org` / `exhentai.org` 畫廊連結 | 顯示畫廊資訊與標籤，附四個動作按鈕 |
| 其他網站的連結 | 預設**沉默**；`REPLY_UNSUPPORTED_LINKS=1` 時回覆 `SUPPORTED_SITES_NOTICE` |
| `t.me` 邀請／公開連結 | 說明它不會加入，也不會替這類連結分類 |
| 一則訊息含多個連結 | X/Twitter 或 Pixiv 作品連結優先，其次是畫廊連結 |

## 功能

**解析**

- 三個站台的連結，其他站點一律不下載、不抓取
- **Pixiv 以原始圖檔送出**，多頁作品變成相簿
- e-hentai 畫廊變成 Telegraph 文章，以**單一訊息**送出，封面就是訊息本體
- 連結冷卻、下載逾時、同時下載數上限、單檔大小上限
- **一位使用者同時只能有一個請求**（只在真的有請求在跑時才拒絕）

**e-hentai**

- **歸檔改用 e-hentai 官方壓縮檔** —— 完全不下載任何一頁
- **標籤顯示繁體中文**，14,324 條對照表
- **平行下載頁面**、百分比進度條、可中止的「停止」按鈕
- **Cloudflare R2 圖片代管**（選用）—— 網址不會過期

**其他**

- **解析快取**：同一個連結不重新下載
- 選用的使用者封鎖名單、各站登入 cookie
- 只有管理員能用的 `/cookies`、`/status`、`/cache`、`/restart`
- 成功後自動清掉機器人送出的「正在解析…」提示；保留使用者的原始連結訊息
- **Telegram 邀請連結**（`t.me/+...`、`t.me/joinchat/...`）會被單獨識別；公開的 `t.me` 連結會辨識但不會被誤標成群組

### 為什麼 Pixiv 是以「檔案」而不是「照片」送出

Telegram 的照片路徑沒有辦法原樣送出一張圖：`sendPhoto` 會在伺服器端重新編碼並改名成 `.jpg`，
所以「照片」永遠不是原檔。依 Pixiv 來源網址強制使用 Telegram 的文件傳送方式，避免呼叫端分類影響結果。靜態圖片、GIF 與影片一律以**文件**送出，包含新解析與快取重送，並關閉自動媒體類型偵測，
檔名使用 `作品名稱_作品ID_p頁碼_畫師ID_畫師暱稱.副檔名`，例如：

```text
夏日作品_150653396_p0_123456_畫師暱稱.jpg
夏日作品_150653396_p1_123456_畫師暱稱.jpg
```

頁碼從 `p0` 開始，快取重送也保留相同檔名。舊版快取會在下次解析時重新下載一次以取得命名資料。
檔名不能使用的字元會替換為 `_`；標題或暱稱過長時會縮短，並保留作品 ID、頁碼、畫師 ID 與副檔名。
改用 ZIP 傳送時，壓縮檔以第一張收錄圖片命名，裡面的每張原檔仍保留各自的頁碼。
Pixiv Ugoira 動圖若下載為影格 ZIP，會依原始順序與播放時間自動合成 GIF，然後直接以 `.gif` 文件傳送，保留原始解析度及全部影格，不縮圖、不刪幀、不合併相同影格。GIF 每幀最多 256 色，播放時間以格式支援的 10 毫秒為單位；這是 GIF 格式本身的限制。檔名使用相同格式，並支援快取重送；舊版 ZIP 快取會重新下載並轉換。GIF 文件若因過大被拒絕，會回報失敗，不額外壓縮或包成 ZIP。

- 圖片會以檔案而不是內嵌照片出現。點開來看，手機上可用「儲存到相簿」，桌機則直接下載
- 多頁作品以最多 10 個為一組，所以 30 頁的作品會是三個相簿，而不是三十則訊息
- 超過 `MAX_UPLOAD_MB` 的檔案會被回報並跳過，而不是悄悄縮小 —— **重點是送出原檔，不是替代品**
- **X/Twitter 仍走一般照片路徑**，因為貼文本來就預期是壓縮過的預覽

### 清理聊天室

請求成功後，機器人只會刪除自己送出的「正在解析…」提示，使用者貼出的原始連結訊息會保留。
用 `.env` 的 `DELETE_STATUS_MESSAGE` 控制是否刪除這則提示；設成 `0` 就保留提示：

```ini
DELETE_STATUS_MESSAGE=1
```

刪除的是機器人自己的訊息，不需要在群組取得刪除他人訊息的管理員權限。

請求**失敗**時什麼都不刪：那時狀態訊息是使用者唯一的解釋，來源連結是他唯一的線索。

#### Pixiv GIF 的桌面文件顯示

Telegram Desktop 會把 MIME 為 image/gif 的文件也顯示成動畫卡片。因此 Pixiv GIF 改用 MTProto，以 application/octet-stream 與強制文件旗標傳送，保留 .gif 檔名及原始 GIF 內容；新解析與快取重送皆適用。請安裝 Telethon 與 python-socks[asyncio]，並在 .env 設定既有的 TELEGRAM_API_ID、TELEGRAM_API_HASH、BOT_TOKEN。登入工作階段儲存在 .mtproto/，與解析快取分開且不納入 Git。缺少設定或連線失敗時會回報失敗，不會降回動畫卡片重送。

#### Pixiv GIF 上傳快取

GIF 除了保留本機解析快取，也會在 .mtproto/documents-cache.json 保存已上傳 Telegram 的文件參照，依 bot、檔案內容 SHA-256 與檔名區分。更新後每個 GIF 首次需上傳一次；之後同一檔案即使來自不同暫存目錄，也可直接重送 Telegram 文件，不重傳檔案內容。參照過期時先從原訊息刷新；原訊息已刪除或參照仍失效，才重新上傳一次。逾時或不確定是否送達時不重送。文件模式與 .gif 檔名維持不變。

## 本機檔案製作 Telegraph

此製作流程僅限 bot 設定中的管理員。非管理員傳送本機檔案、使用 /publish、/cancel_upload 或點選製作按鈕時，不下載、不上傳、不顯示拒絕提示。製作指令僅出現在管理員的專屬選單與說明；一般使用者仍可正常解析支援的網站連結。

每批作品僅建立一則 bot 操作訊息；後續設定、錯誤提示、上傳進度及完成封面均原地編輯。群組輸入設定時，請回覆同一則操作訊息。

**私聊支援圖片與 ZIP／CBZ／7z／RAR；群組僅支援用指令回覆 ZIP／CBZ／7z／RAR。**

在已授權群組中，回覆壓縮檔訊息並輸入 `/publish@機器人名稱`，bot 才會接收該檔案並顯示選單，不會立即上傳。
可沿用私聊的確認／取消、作者／E站連結、頁面文字與連結記憶、製作日期、第一張封面及 R2 去重／重試。
群組設定文字或連結時，請由發起者**回覆 bot 指定的輸入提示**；普通聊天與其他成員的回覆不會寫入設定。
設定記憶依發起者帳號保存，與同一帳號的私聊共用；各群組／各發起者的待製作檔案互相隔離。
直接在群組傳送壓縮檔不會觸發製作，圖片與圖片文件請傳至私聊。重複回覆同一份已接收壓縮檔只會重顯選單。
後續可按「上傳並製作」；也可用 `/publish@機器人名稱` 製作已接收的檔案，或 `/cancel_upload@機器人名稱` 取消。

1. 在 bot 私聊傳送 ZIP／CBZ／7z／RAR 或圖片文件，可累積多個檔案；此時只接收暫存，不上傳 R2。
2. 點「作者連結」或「E站連結」，依提示傳送完整網址；不提供可按「略過／移除連結」。
3. 按「上傳並製作」開始；多張圖片傳完也可輸入 `/publish`，將這批檔案合併為一份作品。
4. 不上傳可按「取消」；`/cancel_upload` 也可取消待製作或正在上傳的作品，頁面建立的最後階段請等待完成。

在接收檔案後的選單，可設定「頁面文字（記憶）」及「文字連結（記憶）」。
頁面標題下方會顯示 `製作日期：2026年11月9日 — 你的文字`，再放排序後的圖片；有設定連結時，自訂文字可點選。
日期在每次建立頁面時以 UTC+8 自動填入。Telegraph 原生的作者欄也會使用自訂文字的第一行（最多 128 字）與連結。
自訂文字最多 2000 字；未設定文字而只有連結時顯示「連結」，只有文字時顯示普通文字。
文字及連結依發送者保存在程式旁的 `local_upload_profiles.json`，下一批及重啟後自動沿用；此設定檔不提交 GitHub。
可重新設定，或在提示下按「清除記憶設定」個別移除。取消當批作品不會清除記憶。
原有「作者」「E站」連結仍僅作用於當批的 Telegram 完成訊息，與上述頁面設定分開。

標題使用第一個收到的檔案名稱（去掉副檔名）；建議以作品名稱命名 ZIP／CBZ／7z／RAR。
圖片按原始檔名自然排序，例如 `2.jpg` 會排在 `10.jpg` 前面；壓縮檔內以完整路徑排序。
Telegraph 內先放標題，再依序放圖片。完成訊息附上排序後第一張圖片作為封面，圖片說明包含「標題」及 `[ 即時預覽 ] / [ 作者 ] / [ E站 ]`，
「即時預覽」連到 Telegraph；「作者」「E站」使用本批使用者提供的連結，未提供的項目保留普通文字。

圖片產生長邊最多 **1280px** 的 JPEG 預覽副本，不放大小圖；透明背景轉白色，GIF 使用第一幀。
原檔保持不變，此流程也不影響 Pixiv 原圖／GIF 文件傳送。
需要沿用既有 R2 設定與可公開讀取的圖片網址；相同內容沿用 R2 物件，不重複上傳。
上傳失敗會提示並自動重試，連續三輪失敗後由發起者選擇再試或停止；停止後不建立頁面。
已成功的圖片不重傳。製作失敗可再次 `/publish`，或 `/cancel_upload` 清除暫存。

每批輸入合計最多 512 MiB、500 張圖片；單張最多 64 MiB／4000 萬像素，ZIP 圖片解壓總量最多 1 GiB。
不接受加密、重複檔名、不安全路徑或符號連結的壓縮檔。超過 Telegraph 頁面上限時會提示分批，不截斷圖片。
下載仍受使用中的 Telegram Bot API 限制；大檔案需使用本機 Bot API。
每份待製作資料依聊天及使用者隔離；閒置超過 24 小時會在接收新檔案時清除，重啟前請先發布。
一般 Telegram「照片」不含原始檔名，會以訊息編號命名；需要保留標題與排序時，請以**文件**或 ZIP／CBZ／7z／RAR 傳送。
私聊同樣套用原有封鎖名單。作者與 E站連結只套用於本批作品，下一批需重新提供。

## 管理員確認傳送 X／Twitter 結果到頻道

1. 以 bot 管理員帳號將 bot 加入頻道，設為頻道管理員並開啟「發布訊息」權限，bot 會自動登記。
2. 在 bot 私聊傳送 X／Twitter 貼文連結。解析完成後，點「傳送到頻道」或「不傳送」。
3. **5 分鐘內未操作，預設不傳送**；逾時選項失效。多個頻道會各自顯示名稱，每次解析只選擇一個目標。

只有 bot 設定中的管理員會得到確認按鈕。一般使用者照常取得解析結果，不會看到頻道選項；群組、Pixiv、e-hentai 與本機檔案製作不會出現此選項。新解析與快取重送均支援。

管理員可在私聊輸入 `/channels` 查詢頻道；若 bot 已在頻道中、未收到加入事件，可使用
`/channels @頻道名稱` 或 `/channels -100頻道ID` 手動登記。私密頻道使用數字 ID。
`/channels remove -100頻道ID` 移除傳送選項。未登記頻道時不會自動發布。

確認後會複製該次私聊已送出的媒體及說明，保留相簿與來源連結，不重新下載、不複製處理提示。
發布前會重新檢查管理員與頻道發布權限；移除 bot 或撤銷發布權限後，頻道會從清單移除。
每次確認只能使用一次。傳送逾時或僅複製部分結果時會提示檢查頻道，不自動重送。
頻道清單保存在程式旁的 `channel_targets.json`，不提交 GitHub；確認選項不跨重啟保存，重啟後不會補發。

## 使用方式

### 指令與權限

| 指令 | 誰能用 | 說明 |
| --- | --- | --- |
| `/start`、`/help` | 任何人 | 只有用法說明，不含部署細節 |
| `/id` | 任何人 | 顯示自己的 ID |
| `/authorized` | bot 管理員 | 目前的名單、模式，以及正在使用的檔案 |
| `/grant <ID>` | bot 管理員 | 私人聊天：解除封鎖某人。群組中不帶 ID：授權**該群組** |
| `/revoke <ID>` | bot 管理員 | 私人聊天：封鎖某人。群組中不帶 ID：移除**該群組**的授權 |
| `/blocked` | bot 管理員 | 列出被封鎖的使用者 |
| `/promote <ID>` | **僅管理員** | 把某人升為管理員 |
| `/demote <ID>` | **僅管理員** | 移除管理員權限 |
| `/lockgroup on\|off` | **僅管理員** | 群組模式的開關 |
| `/cookies` | **僅管理員** | 憑證檔、到期日、錯誤字串 |
| `/status` | **僅管理員** | 各項上限、授權狀態、執行期設定 |
| `/cache` | **僅管理員** | 解析快取內容；`/cache clear` 清空 |
| `/audit` | **僅管理員** | 對每一個套件查 OSV 漏洞資料庫 |
| `/restart` | **僅管理員** | 用一份全新的行程取代正在跑的這一份 |

**解析對所有人開放。** 私人聊天用的是**封鎖名單**：名單為空代表任何人都能解析，把某人加進去
只是擋掉他，不會給他原本沒有的東西。群組則刻意維持**允許名單**：公開群組裡的機器人應該只服務
「被刻意加進去」的群組，而不是每一個剛好把它拉進去的群組。

| 名單 | 空白 | 有名單 |
| --- | --- | --- |
| **私人聊天**（封鎖名單）| 所有人都能解析 | 名單上的人被拒絕，其他人歡迎 |
| **群組**（允許名單）| 由 `AUTH_GROUP_LOCKED` 決定：全開或全關 | 只有名單上的群組 |

**管理員在兩種模式下都能通行**，所以名單寫錯也不會把操作者鎖在自己的機器人外面。
私人聊天不受群組名單與群組模式影響，群組也不受封鎖名單影響 —— 私人聊天沒有群組能替它發言，
所以套用使用者規則。

`/lock` 已經退役（封鎖名單不是一道閘門，沒有「模式」可選），但仍註冊著並會回答「它被什麼取代」，
因為筆記裡還留著 `/lock` 的人一定會輸入它。

**授權整個群組：** 在群組裡打 `/grant`、不帶參數，那個群組就被授權了：其中每個成員都能解析，
不必逐一授權。這是實務上的用法，因為聊天 ID 用手找很麻煩。

```
1. /lockgroup on          → 守門模式；目前沒有任何群組能解析
2. /grant   （在群組裡）  → 該群組成為唯一能解析的群組
3. 其他任何群組           → 仍然被拒絕
```

`/lockgroup on` 在群組名單為空時是**允許**的：它會先擋住所有群組，直到有人被授權為止，
回覆也會這樣說。先守門、再到群組裡 `/grant`，是自然的順序；擋掉它反而會擋掉讓這個功能可用的
那套流程。管理員隨時可以在私人聊天裡用 `/lockgroup off` 復原，所以沒有任何回不去的狀態。
在群組裡 `/revoke` 會移除該群組授權，保留既有守門設定；名單變空時仍依原有模式決定可用範圍。

三件值得知道的事：**在群組裡管理名單只有管理員能做**（群組授權是在群組裡決定的，如果任何授權使用者
都能改，被授權群組裡的任何成員都能改名單）；**管理員到處通行**，包括不在名單上的群組；
**私人聊天與群組的規則互不影響**。

**第一個管理員只能來自 `.env`**，因為那時沒有人能授權它：

```ini
ADMIN_USER_IDS=123456789
```

之後重啟一次，其餘都在 Telegram 裡用 `/promote` 完成 —— 這就是這個介面的意義：
改授權不該需要碰主機。傳 `/id` 可得知自己的數字 ID；**只接受數字 ID，永不接受 `@username`**，
因為使用者名稱可以被改掉、被別人重新註冊，記在使用者名稱上的授權遲早會指向另一個人。
**`ADMIN_USER_IDS` 空白不代表「所有人都是管理員」**，而是管理指令對所有人關閉並告訴擁有者怎麼開啟；
在公開機器人上，相反的預設會把 `/cookies` 交給任何陌生人。

名單的變更寫進 `bot.py` 旁邊的 `authorized.json`，重啟後仍然有效，也包含群組聊天 ID
（負數，超級群組是 `-100…` 的形式）。`.env` 提供起始值，檔案保存指令改過的部分。
檔案損壞或讀不到時會退回 `.env` 的值並在日誌說明，而不是崩潰或默默放寬權限；
改動名單的指令也會在聊天裡回報寫入失敗，所以「重啟後會消失的變更」不會看起來像有效的變更。
這個檔案已被 gitignore（裡面是真實的使用者 ID）。管理指令不會出現在公開的 Telegram 指令選單裡，
bot 管理員則會拿到依自己聊天室範圍的選單。

### 按鈕

畫廊結果上的行內按鈕才是實際操作的地方：

| 按鈕 | 做什麼 |
| --- | --- |
| `Telegraph · 顯示圖` | 發佈一個嵌入站方 1280px 圖片的 Telegraph 頁面，什麼都不送進聊天室 |
| `Telegraph · 原圖` | 發佈嵌入全解析度圖片的 Telegraph 頁面 |
| `歸檔 · 1280` | 下載 1280px 版本，打包成一個 ZIP 送出 |
| `歸檔 · 原圖` | 下載全解析度版本，打包成一個 ZIP 送出 |
| `重新生成 Telegraph 頁面` | 重新取得簽章網址並原地更新頁面 |
| `停止` | 中止進行中的下載 |

按下按鈕之前什麼都不會下載，所以「只是好奇」的連結只花一次 metadata 請求。

### 在 Telegram 群組裡使用

- 把機器人加進群組
- 如果機器人需要看到一般的群組訊息，用 `@BotFather` → `/setprivacy` → 選擇機器人 → `Disable`，
  然後把機器人移除再重新加入群組
- 或者在隱私模式允許的範圍內，由使用者提及／回覆機器人
- 除非真的需要管理權限，不要把它設成群組管理員

**在隱私模式關閉的部署上（`can_read_all_group_messages: True`），Telegram 會送來每一則群組訊息**，
包含完全沒有東西可解析的那些。兩條規則讓這件事不至於變成噪音：

- **沒有連結的訊息永不回覆**，無條件。它以前會在「看起來」被叫到時回覆說明文字 —— 例如被 `@` 提及，
  或有人回覆它自己的訊息 —— 結果被回報成「機器人被別人觸發」：有人回覆機器人先前貼的照片、
  寫了一句「如此巨乳！」，機器人就用使用說明回答。任何這類猜測都是對意圖的賭注，
  而猜錯比沉默更糟；`/help` 明確涵蓋了合法情境，而且不會誤觸。
- **授權檢查在找到連結之後才做。** 以前是先檢查，於是未授權使用者的每一句話都會收到
  「此機器人目前不允許你的帳號使用」，連「i send no link」這種話也一樣。這就是調整順序要修的誤判。

被拒絕的使用者永遠到不了快取、下載器或 Telegraph：閘門在它們全部之前，回歸測試也會斷言被拒絕的
使用者根本不會觸發查詢。**被拒絕的群組則是完全沉默，而不是回一句拒絕**：拒絕訊息在私人聊天裡是
有用的答案，在群組裡恰恰相反 —— 它會在別人的對話裡對每一則連結出聲，還向沒在問它的人宣傳自己的存在。
這個守衛是 `handle_message` 的第一件事，所以被拒絕的群組連冷卻提示、不支援連結提示、失敗訊息都到不了。

### 請求、冷卻與失敗回覆

一位使用者同時只能有**一個**請求在跑。第二個會被拒絕並說明現在的情況，第一個一結束就立刻接受。

這取代了過去對所有東西（包含按鈕）一律套用的 10 秒冷卻：那個版本會在有人剛完成一個動作、
馬上按下第二個時跳出「操作太快了」—— 明明沒有東西在跑，剩餘冷卻還在倒數 —— 於是它拖慢了真正的
工作，卻沒有增加任何保護。**「距離上次請求多久」不是重點，「現在有沒有工作在跑」才是。**
連結保留自己的冷卻，因為貼連結會啟動真正的下載工作，重複張貼才是濫用情境；按鈕不受此限制。

```ini
USER_COOLDOWN_SECONDS=10   # 只針對連結
REQUEST_STALE_SECONDS=1800 # 請求沒釋放名額就卡死時，回收它
```

名額一定會被釋放（包含工作拋出例外），而卡死上限意味著任何當機都不會永久鎖住一位使用者。

**失敗回覆只有一行**，技術診斷 —— 憑證狀態、`bot.py --check --live` 指令列、例外類型 ——
**寫進日誌而不是聊天室**：

```
取不到連結內容，可能是平台限制，請稍後再試。

原始連結：https://x.com/...
```

以前這些會在使用者要求時附加在回覆裡，結果操作者在對話中間看到一整段 shell 指令。
資訊沒有消失：它在主控台日誌與 `restart.log` 裡，`/cookies` 也能隨時回報憑證狀態。
`@BotFather` 的隱私模式步驟刻意**不出現在任何聊天回覆裡**，因為那是部署細節。

**不支援的連結預設沉默**（`REPLY_UNSUPPORTED_LINKS=0`）：公開群組裡對每一則無法解析的連結都回話，
只是在沒被邀請的對話裡製造噪音。想換成別的訊息，或想在看連結是真的不支援、還是被誤判時打開它：

```ini
SUPPORTED_SITES_NOTICE=目前只支援 X/Twitter、Pixiv 與 e-hentai 連結。
REPLY_UNSUPPORTED_LINKS=1
```

沉默之所以安全，是因為**分類照樣會跑**：不是貼文的 X 連結仍會在啟動下載器之前被辨識並丟掉，
否則「沉默」會變成等三分鐘然後什麼都沒聽到。

### /restart

不需要碰主機就能重啟，這正是重點：否則改 `.env` 或換憑證檔都得去碰機器。
它只給管理員用，因為它會讓機器人短暫離線。

1. 啟動 `bot.py` 的第二份副本，**分離**執行，不屬於啟動目前這份的控制台。
   副本會先等幾秒才開始 polling，免得跟它要取代的行程搶 Telegram 的 `getUpdates` 鎖
2. 回覆新行程的 PID 與日誌路徑
3. 短暫延遲後停止 polling，讓那則回覆先送達 Telegram，也讓進行中的更新跑完

新副本會寫入 `bot.py` 旁邊的 `restart.log`，機器人沒回來就讀那個檔。啟動失敗會在聊天裡回報，
而且**目前這個行程會繼續跑** —— 一場沒發生的重啟，不能看起來像發生過。

```ini
RESTART_STARTUP_DELAY=6      # 替代行程開始 polling 前等待的秒數（上限）
RESTART_LOG_MAX_MB=2         # restart.log 超過這個大小就輪替
```

實作上踩到的四個失敗模式（`stop_running()` 在錯的執行緒被呼叫、兩個 poller 搶同一個 token、
子行程繼承 stdout 管線導致啟動器永遠等不到 EOF、`restart.log` 用系統代碼頁寫成亂碼），
以及「重啟後沒有視窗」、「每次啟動都等六秒」兩個症狀，完整記錄在 [docs/NOTES.md](../docs/NOTES.md)。

#### 匿名群組管理員

支援以本群組身分發言的匿名管理員：在群內使用不帶參數的 /grant 授權本群，或 /revoke 移除本群授權。Telegram 不公開匿名管理員真實使用者 ID，因此不能透過匿名身分操作其他群組、指定使用者 ID 或執行 bot 全域管理命令；請改用設定中的管理員帳號以個人身分執行。其他頻道代發與自動轉發不會被視為本群匿名管理員。

/grant 授權或解除封鎖成功後，bot 的成功提示會顯示 5 秒再自動刪除；原始指令訊息保留。沿用 DELETE_STATUS_MESSAGE 設定，設為 0 時保留提示；授權資料寫入失敗的警告不自動刪除。

### e-hentai 頁面與封面

Telegraph 的文字僅保留原標題與日文標題，不加入標籤或畫廊資料；圖片照常依序排列。Telegram 完成訊息使用實際第一頁大圖作為封面。舊快取頁面下次解析時會原地更新版型，網址不變。

原標題若使 Telegraph 建頁回傳 `PAGE_SAVE_FAILED`，會改以短網址建立後恢復原標題；文章中的原標題、日文標題及圖片不變。

### e-hentai 獨立頻道發布

管理員在私聊使用「Telegraph · 顯示圖」，頁面製作成功且顯示封面後，才會出現傳送至 EH 頻道的選項；5 分鐘未選擇預設不發布。歸檔、重新生成、取消、製作失敗及純文字備援不顯示發布選項，一般使用者也不顯示。

以 `/ehchannels @頻道名稱` 或 `/ehchannels -100頻道ID` 登記目標；`/ehchannels` 查詢，`/ehchannels remove -100頻道ID` 移除。bot 須有該頻道的發布權限。EH 目標清單、確認選項與 Twitter 的 `/channels` 完全分開，不會自動沿用 Twitter 頻道。

### 頻道發布前檢查重複連結

確認發布後，bot 會唯讀檢查所選頻道的歷史訊息、圖片說明及隱藏超連結；已有相同來源或預覽連結就不傳送，並提示原訊息編號。Twitter 的追蹤參數、x.com／twitter.com，以及 e-hentai／exhentai 的同作品網址會合併比對。不同頻道各自檢查。

此功能沿用 GIF 文件模式的 `TELEGRAM_API_ID`、`TELEGRAM_API_HASH` 與 bot MTProto 工作階段，不需登入個人帳號。歷史訊息較多時檢查會較久；遇到 Telegram 限流會依服務要求等待（最多自動等待 60 秒），讀取失敗則本次不發布。只讀取訊息，不標記已讀或傳送測試訊息。

### 管理員私聊的 exviewer 既有預覽

管理員在私聊直接傳送 EH 連結，bot 會先查詢 `@exviewer_bot`。命中時取用既有 Telegraph 預覽並保留原文與超連結，不顯示轉發來源標頭，也不重新上傳 R2 或建立頁面。接著可選擇是否發布至 EH 頻道；既有 5 分鐘逾時不發布與頻道重複連結檢查照常生效。

只有畫廊 ID、token 與來源網址一致的結果才取用。沒有結果、資格不足、未登入或查詢逾時時，維持原本本機解析。一般使用者私聊不查詢 exviewer；已授權群組可查詢，但不顯示頻道發布選項。

頻道連結檢查使用持久化索引：首次讀取完整歷史，之後只同步新增、編輯及刪除。Telegram 無法提供完整增量時才重建；不以過期索引放行。

取用 exviewer 的 EH 結果亦提供「官方壓縮包 · 1280／原圖」下載按鈕；下載沿用現有 EH 歸檔流程，頻道發布規則不變。
